# 账号模型自然月消费额度

本功能在已有账号模型额度上增加完整自然月续窗。范围仍是一个零售钱包账号、一个精确的公开模型名称和 USD 消费金额；该账号不同 Key、资源池的请求共用额度。它不增加组织资金账户，也不改变已有价格快照和实际钱包扣款

R10 已完成本地 API、双 worker、实际浏览器和有界数据库对照验收，生产未改动。完整实现提交为 `1b96ba5cfdd52d9c1c45f2bbce4294b5f0fdd3d4`，证据见 [R10 验收](validation/r10-2026-11-04.md)；分组计数和运行状态单独记录

## 月份、金额和首次生效

只支持 `UTC`、`Asia/Shanghai` 两个时区。每个窗口采用当地自然月的左闭右开区间 `[月初, 下月月初)`，底层保存 UTC 时间。时区一经创建不能修改

首次开始月份必须是服务器当前日期的下一个完整自然月或更晚月份；客户端提交 `YYYY-MM`，不能填写任意开始时间、当月剩余时间或历史月份。首次开始之前，不把当前月已有请求追算进新计划

例如，在 2026-11-04 创建从 `2026-12` 开始的计划：

| 时区 | UTC 开始时间 | UTC 结束时间 |
| --- | --- | --- |
| `UTC` | `2026-12-01T00:00:00Z` | `2027-01-01T00:00:00Z` |
| `Asia/Shanghai` | `2026-11-30T16:00:00Z` | `2026-12-31T16:00:00Z` |

金额沿用整数纳美元，`1 USD = 1,000,000,000 nanos`。接口通过最多九位小数的正数 USD 字符串传输，不接受浮点数金额、多币种换算、通配模型或业务标签匹配。预算消费来自零售实际费用，不使用原生 provider Spend 代替

计划与已存在的手动窗口不能重叠。可以先保留一个在计划开始前结束的手动窗口。尚未取消的计划也会阻止随后创建与其范围重叠的手动窗口

## 修改与停止

调整计划金额只影响尚未开始的完整月份。服务器把新金额写入未来生效的 terms，已开始窗口的金额、日期和启用状态被冻结。未开始的已生成子窗口同步采用新金额；尚未生成的窗口由 worker 按该月份适用的 terms 创建

`limit_usd` 是最新计划金额，必须与 `limit_effective_from` 一起展示。它可能是下月或首次开始月份的金额，不能直接解释成本月已生效额度。本月实际额度、占用和消费仍看对应的模型预算窗口

计划状态为 `scheduled`、`active`、`stopping` 或 `stopped`。`current_window_ready` 另行说明当前预算窗口是否就绪；尚未到首月时为 false 属正常情况，已经生效的计划为 false 时应核对续窗故障，不能理解为没有限制

停止是管理员明确结束未来续窗的操作，不等于立即放宽本月限制：

| 停止时的情况 | 结果 |
| --- | --- |
| 计划已开始 | `stops_at` 为当地下一月月初。本月继续限制，尚未开始的子窗口取消限制，之后不再自动续窗 |
| 首月尚未开始 | `stops_at = starts_at`，计划不进入生效月份，已预建子窗口取消限制 |

取消的子窗口保留记录，不删除或清零。请求准入排除已明确取消的未来窗口，允许在不重叠的时间范围创建新计划。已经停止的计划不能恢复；如需重新启用，应创建新的计划并重新核对开始月份

模型预算列表的 `recurrence_id` 对普通手动窗口默认为 `null`，对子窗口为其计划的 opaque ID。子窗口不能通过旧的 Edit、Pause/Resume 或 Schedule next window 接口偷偷改写，应回到续窗计划调整或停止；管理接口对此返回 409

## 请求接纳与晚到结算

沿用已有钱包锁、预估预留、模型额度 allocation 和幂等终态处理。接纳后的请求固定绑定其预算窗口，跨月、停止计划或修改未来金额，都不会把旧请求迁移到新窗口

请求实际结算时，占用转为消费；正常释放后收到有效的晚到结算，仍计入原窗口。已有人工释放、未知用量、事实冲突和待结算请求保持原来的处理规则，不能因跨月自动释放或按零结算。实际费用可能高于预估，占用不是绝对费用上界；已发生费用仍据实入账，因此本功能不承诺绝对零超支

计划在生效月份具有持久的“应有预算窗口”约束。当前 occurrence 尚未创建、不可用或不符合约束时，服务端拒绝新请求，不把“没有查到预算”当作无限额。新版本在原预留 SQL 的同一次数据库调用中检查；缺窗沿用 `budget_exceeded` 的固定 HTTP 429 提示。旧版本触发数据库保护时可能得到存储不可用错误，也不允许放行

关闭管理或 worker 开关不会删除这项持久约束，也不会绕过已保存窗口。预算、钱包余额、账号权限以及 RPM/TPM 等限制分别检查

## 后台续窗与故障恢复

worker 每批最多处理 20 个到期计划，只生成当前月份和下一月份所需的 occurrence。首次开始月份更晚时，等待进入相应预建范围。并发 worker 使用钱包锁和计划锁，以及 occurrence 的唯一键，避免重复创建；预算表和账本仍是权威，不依赖 Redis 中的临时计数

停机跨越一个或多个月份后，恢复时只补当前月及下一月，不补造已经结束的历史窗口，也不追算停机期间未接纳的请求。计划金额的历史 terms 仍保留；当前月缺窗时，即使管理员修改了下月金额，恢复生成本月窗口也使用本月原 terms

暂停 worker 期间已经预建的窗口继续生效；预建范围用尽后，持久约束会拒绝缺窗请求。因此关闭开关只能暂停新入口和后台工作，不能作为安全“取消预算”的操作。需要结束未来限制时，应先由管理员明确停止计划并核对 `stops_at`

worker 复用已有有界诊断连接池，不新增连接池或线程池。空闲或忙钱包被跳过时等待 10 秒再检查；单个计划处理失败后推迟约 60 秒再尝试。忙钱包使用 `SKIP LOCKED`，不会为了续窗长期占住推理钱包行锁。控制面 SQL 有 500 ms 锁等待、3 s 单语句超时；这些是资源边界，不是端到端续窗或请求延迟承诺

停止 worker 会取消未完成的当前事务，已提交窗口保留，重启后按持久状态继续。审计不可写时，计划创建、调额或停止也回滚，不返回无审计的成功变更

## 权限与接口契约

只有当前可写全站 Proxy Admin 可以为指定账号创建、调额和停止计划。普通用户只能查询自己的计划；组织成员关系或委派财务 View/export 不赋予预算写权限。管理员和个人请求均需由 API 层重新验证当前原生账号、凭据和角色，不能只相信浏览器或旧缓存

以下是已接线的 R10 接口契约，HTTP 与浏览器证据见本批验收记录

| 路径 | 用途 |
| --- | --- |
| `GET/POST /retail/admin/users/{user_id}/monthly-budgets` | 全站管理员分页查询或创建计划 |
| `GET/PATCH /retail/admin/users/{user_id}/monthly-budgets/{monthly_id}` | 查询详情或修改未来金额 |
| `POST /retail/admin/users/{user_id}/monthly-budgets/{monthly_id}/stop` | 明确停止未来续窗 |
| `GET /retail/monthly-budgets` | 本人计划列表 |
| `GET /retail/monthly-budgets/{monthly_id}` | 本人计划详情 |

创建字段为 `model`、`start_month`、`timezone`、`limit_usd`，以及固定 `currency: "USD"`。调额提交 `limit_usd` 和严格整数 `expected_version`，停止只提交 `expected_version`。管理写入要求 `Idempotency-Key`：同键同内容重放原结果，键冲突或版本冲突返回 409；不要把重放的旧确认响应当作重新授予或当前状态，应重新读取计划

列表仅接受有界的 `q/limit/offset`，未知查询和请求体字段拒绝。个人投影只返回本人计划的必要信息，不包含管理操作者、来源人员或其他账号 ID。响应沿用 `private, no-store`；错误不回显原始敏感输入

成功操作以 `monthly_budget.created`、`monthly_budget.updated`、`monthly_budget.stopped` 记录全站私有审计，资源类型为 `monthly_budget`。计划、terms、子窗口和事件在同一个 retail PostgreSQL 事务中提交。事件不作为钱包扣费证据，也不保存凭据、原始请求正文或供应商成本

## 配置、初始化和请求路径

`RETAIL_MONTHLY_BUDGETS_ENABLED` 默认 `false`，依赖同时启用：

```dotenv
RETAIL_OPERATION_AUDIT_ENABLED=true
RETAIL_MODEL_BUDGETS_ENABLED=true
RETAIL_MONTHLY_BUDGETS_ENABLED=true
```

默认关闭代表不开放新计划入口和续窗 worker，不代表撤销已经持久化的计划。基础钱包初始化始终建立以下小表及保护逻辑，使有计划的账号在页面或 worker 关闭时继续保持约束：

| 表 | 内容 |
| --- | --- |
| `retail_model_budget_recurrences` | 账号模型、时区、首次月份、明确停止边界、配置版本和下次检查时间 |
| `retail_model_budget_recurrence_terms` | 每个未来生效月份适用的整数金额 |
| `retail_model_budget_occurrences` | 完整月份与既有模型预算 policy 的固定映射 |

初始化只建结构、索引和保护函数，不重写历史钱包、账本或预算行。子窗口继续使用原来的 policy/allocation 表，不另建扣费权威

新逻辑在既有预留 SQL 内增加有索引的计划与 occurrence 检查，数据库还在 reservation 插入时执行持久保护。没有增加独立的逐请求 driver 调用、外部 RPC、历史流水聚合或每个 SSE 分块写库；这不等于数据库内部完全没有新增工作。终态结算、释放和账本写入 SQL 保持原行为。容量与尾延迟仍须以相同负载的实际对照为准，核心测试不能证明 20,000 RPM 生产容量

## 升级和回滚边界

先升级全部参与财务写入的 worker 与后台进程，再启用开关、创建首个计划。核心财务保护首次合入主分支为 `849956ae`；部署须使用包含本批 API、worker lifecycle 和 UI 的完整实现，具体版本以本批验收记录为准，不能只部署核心提交

数据库独立保护会在旧程序重载旧 `budget_schema.sql` 后继续阻止缺 occurrence 的 reservation，并保护已开始窗口的配置。独立的 policy 插入保护还会拒绝旧 guard 将完整月份改成“从现在开始”的部分窗口。已经绑定的 allocation 仍可以按原窗口结算

这些保护保证安全拒绝，不保证旧程序正常可用。旧程序不认识计划、terms、取消窗口的过滤或新建月窗通道，混跑可能无法续窗、拒绝请求或因多候选 policy 而事务失败。不能把“关 flag + 回滚旧二进制”描述为无感或兼容回滚

需要回滚时，保留所有新表和数据库保护，停止不兼容的财务写入进程，并保留支持持久约束的请求准入与终态处理。可以关闭新管理入口、暂停新计划，或由可写管理员明确停止未来计划；本月窗口与既有请求不能通过删表、删 trigger、清计数或关闭 flag 撤销。恢复完整新版后检查当前/下一 occurrence 与未决请求，再恢复流量
