# 账号按模型的固定窗口消费额度

本模块限制已接入零售钱包计费链路的新请求，范围为同一账号、同一个精确公开模型名称。该账号的不同 Key、不同资源池共用该额度，不按上游部署、当前业务标签或组织成员关系划分

## 使用方法

全站 Proxy Admin 在 Customer Wallets 的账号行打开 Model budgets，选择公开请求模型、填写 USD 额度与北京时间结束时间。生效时间由服务器取得钱包锁后填写，不能由客户端伪造或回填

首版采用明确的固定窗口，结束时间最多晚于生效时间 366 天，不自动按自然月重置。不追溯历史用量，也不统计窗口生效前已经接纳的在途请求。同一账号模型的窗口不能重叠，暂停的窗口也保留其时间范围

创建后可以调整额度或暂停、恢复。账号、模型、生效时间和结束时间不能修改，历史窗口不能删除或清零。到期后可建立新窗口，旧窗口的在途请求继续归原窗口结算

个人 Wallet 页面只显示本人的模型、额度、已结算金额、占用额、剩余可接纳额度、窗口及状态。普通用户没有创建、调额、暂停或重置入口，不返回管理来源、修改人或其他账号标识

## 费用与占用

金额以整数纳美元计算，并通过九位小数的 USD 字符串传输，不经过浮点数转换。页面中的预算消费来自零售钱包费用，不使用原生 provider Spend 作为客户消费

在既有钱包预扣事务中，服务端同时检查当前窗口的已结算金额、在途占用和本次预估额度。启用且不足时拒绝新请求；成功接纳后保存请求与窗口的固定绑定

额度不足返回 HTTP 429，公开类型和代码为 `budget_exceeded`，使用固定的预算窗口提示，不透传原始诊断。它与普通 RPM 或并发限流不同，不能仅靠等待重试判断恢复

请求实际结算时，占用转为真实消费；确认无可计费用量的失败才释放占用。未知用量、事实冲突、结算待处理和活动租约到期不会自动释放额度或记为零。重复终态只记一次

预估额度不是所有上游费用的绝对上界。实际用量高于预估时仍然据实扣款并计入额度消费，可以出现超额；之后新请求按最新占用拒绝。额度控制不能抹掉已经发生的可计费用量，也不承诺绝对零超支

正常释放后收到有效的晚到结算时，真实消费仍记入原窗口，不再重复减占用。已经由管理员明确释放的请求，沿用原有冲突处理，不自动推翻人工处理

## 暂停、调整和到期

暂停仅停止对新请求进行此额度上限判断，窗口内新请求仍跟踪占用和实际消费；恢复不重置已有数字。钱包余额、账号授权和其他限流继续独立检查

调低额度可以低于已结算金额与占用之和，但不取消已接纳请求。调高后新请求读取新配置；配置版本与财务计数版本分开，不因每次结算导致管理表单无效

结束时间只决定新接纳请求是否进入该窗口。窗口到期不会取消旧请求、释放未知占用或迁移其费用，新窗口的用量与旧窗口分别保留

## 权限、审计与故障

管理接口逐次核验当前原生管理员身份与目标账号，个人查询只接受模型搜索及分页，不能提交另一个 user_id。响应和验证错误使用 `private, no-store`，非法输入不原样回显

管理写入要求幂等标识和配置版本，成功修改与操作事件在同一个 retail PostgreSQL 事务中提交。409 要求刷新后核对再编辑；503 不得解释为无限额或无规则

计数以 PostgreSQL 为权威，沿用钱包锁、事务和有界连接池，不依赖 Redis 中的非持久临时额度。协调 Redis 失效仍按已有严格保护拒绝新凭据请求；已开始请求的终态处理继续保留财务事实

## 配置与请求路径

`RETAIL_MODEL_BUDGETS_ENABLED` 默认关闭且依赖审计，仅控制管理与查询入口。已经保存的窗口仍参与请求准入与终态处理，关闭页面开关不会撤销现有财务限制

预算表与基础钱包表一同初始化。部署时所有参与财务写入的 worker 必须先升级，再创建额度规则；旧版程序不认识新规则，不能作为有规则时的兼容回滚方案

预留、结算、释放使用现有财务事务，将额度逻辑合入原来的 SQL 语句，不增加独立远程事务或逐请求历史聚合，不在每个流式分块中写数据库。终态事实关键池继续独立持久化，管理请求使用有界诊断连接

当前仅覆盖原有零售钱包计费路径。全站管理员调用、关闭零售计费、尚未接入的钱包外异步对象、标签预算、优先级额度、组织共享额度与自动自然月续期不属于本批范围。内部终态重试幂等不等于客户端重试自动去重
