# Retail request body limits

The independent `RequestBodyLimitMiddleware` reads `RETAIL_MAX_REQUEST_BYTES` once when created. The default `0` disables it. The allowed range is 0 through 1 GiB, in bytes. A local value of `33554432` enables a 32 MiB ceiling. Production must choose and explicitly enable its own limit

The ceiling applies to every HTTP method and path, including DELETE, unusual GET bodies, custom passthrough routes, multipart forms, audio, and file uploads. WebSocket and lifespan traffic pass through. This module does not alter the native size middleware, its license checks, response sizes, or SSE output limits

A declared Content-Length above the ceiling returns 413 without reading the body or entering the application. Invalid or duplicate Content-Length headers return 400. Accepted requests are read only when the existing application asks for a chunk. The guard counts actual wire bytes, including chunked requests and requests with an understated or absent Content-Length. It neither reads ahead nor collects a second body buffer. The chunk that crosses the ceiling is not passed to the application, and the rest of the upload is not drained

The guard must wrap body parsing and request tracing. Existing JSON inference handlers parse the complete request before opening their upstream request, so an unknown-length oversized JSON request fails before forwarding. Native handlers sometimes translate receive exceptions; the guard preserves a known overflow as 413 if the response has not started. Custom upload handlers that intentionally forward each incoming chunk can already have sent an accepted prefix upstream before an unknown-length request crosses the ceiling. Preventing that requires buffering or spooling and is outside this module. If such a handler already sent response headers, the guard aborts rather than sending a second status line

Unsupported Content-Encoding returns 415 only for known JSON inference scope: direct chat/completions, completions, messages, messages/count_tokens, responses, embeddings, images/generations, audio/speech, rerank, search and moderations endpoints with an optional numeric version prefix; `/openai/`, `/openai_passthrough/`, `/anthropic/`, `/gemini/` and `/vertex_ai/` namespaces; and model methods ending in generateContent, streamGenerateContent, countTokens, predict, rawPredict or streamRawPredict. Declared application/json and +json are JSON; missing Content-Type is treated as JSON only for those direct endpoints or model methods. Identity encoding remains supported

Explicit multipart, audio, octet-stream and other non-JSON content types keep their existing encoding semantics. Unknown custom passthrough encoding is also preserved. These requests are still subject to the global wire-byte ceiling, which is not a decompressed-size guarantee. The guard never decompresses a request

The local ASGI and HTTP boundary tests cover early rejection, chunked and understated lengths, all HTTP methods, exact-limit acceptance without extra reads or copied messages, malformed headers, encoding scope, unchanged upload forwarding, native error translation, and zero upstream requests for oversized JSON
